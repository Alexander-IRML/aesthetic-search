# ArtSearch v0.7.0

Release date: 2026-09-14

## Release Summary

v0.7.0 turns the public alpha into a bounded stream-day deployment and adds the
control-plane foundation for growing ArtSearch beyond a hand-maintained corpus.
The release combines four related milestones:

1. a continuously expandable, provenance-aware Bluesky creator graph;
2. a budget-gated path from managed Qdrant to ten million compressed vectors;
3. asynchronous query serving with explicit model backpressure; and
4. a three-shard public demo with experimental retrieval controls and visitor
   telemetry.

The public search page remains available at:

`https://artsearch-alpha-search.aesthetic-search-alpha.workers.dev/search`

The ten-million target is an implemented migration path and operating contract,
not a claim that the current hosted alpha already contains ten million artworks.

## Current End-To-End Architecture

```text
Offline corpus growth
  Bluesky seeds and social-neighbor suggestions
    -> stable DID deduplication and provenance graph
    -> bounded profile and media sampling
    -> SigLIP artwork gate and creator qualification
    -> accepted originals in private R2
    -> PostgreSQL catalog, lineage, workflow, and audit records
    -> CLIP subject + CSD style embedding jobs
    -> Qdrant named-vector index and active alias

Online image query
  Cloudflare static workbench
    -> per-IP and per-location edge controls
    -> deterministic choice of one of three Container shards
    -> bounded CLIP/CSD CPU model owner
    -> asynchronous Qdrant CLIP/CSD recall and reciprocal-rank fusion
    -> asynchronous Neon catalog and telemetry
    -> top ten approved images streamed from private R2
    -> optional metadata-grounded Workers AI summary
```

Every durable handoff retains model, index, configuration, source, and decision
lineage. Corpus discovery never bypasses the per-image artwork gate, and social
proximity is not represented as visual similarity.

## Corpus Discovery And Controls

The new `artsearch.discovery` package implements a bounded creator-discovery
campaign rather than an uncontrolled crawler. PostgreSQL stores source
suggestions, stable creator DIDs, graph edges, creator qualification evidence,
frontier tasks, exclusions, human decisions, and removal requests.

The default process is:

1. resolve a candidate to a stable DID and record every discovery source;
2. reject duplicate account work while retaining distinct edge provenance;
3. check exclusion and safety state before downloading media;
4. sample a small initial portfolio and run it through the existing SigLIP
   pipeline;
5. score artwork density, acceptance rate, originality, source reliability, and
   novelty;
6. deepen only qualified or explicitly reviewed creators; and
7. enqueue bounded social-neighbor expansion from qualified creators.

A creator can contribute at most 25 unique child accounts across outbound-follow
and suggested-follow expansion. Duplicate DIDs are counted in campaign metrics
but are not sampled again while equivalent work or fresh evidence already exists.

The local model-operations application now includes a corpus-control view. It
shows compact artist and post keys, current graph edges, qualification state,
and pull history. An operator can launch either of these background operations:

- pull posts not already represented for current corpus artists;
- expand one to three graph steps from rotating current-corpus seeds with an
  explicit request budget.

See [`docs/corpus_discovery.md`](../corpus_discovery.md) for the data model,
scoring policy, commands, and remaining discovery sources.

## Budget-Constrained Retrieval Path

The live alpha continues to use managed Qdrant named vectors because the current
corpus and traffic fit that service well. v0.7.0 also introduces a common async
retrieval contract and a compressed FAISS snapshot backend so the project has a
measured escape path before managed RAM becomes the dominant cost.

The ten-million design includes:

- normalized CLIP and CSD vectors stored as compact archive values;
- immutable, versioned FAISS snapshots with manifests and checksums;
- exact model-bundle and index-lineage validation before promotion;
- configurable flat-to-HNSW transition and training samples;
- retention policy and orphan cleanup with dry-run support;
- capacity estimates and a hard USD 50/month planning gate; and
- exact-versus-ANN recall and latency promotion criteria.

This release does not silently switch the public alpha away from Qdrant. Backend
selection is explicit and the active contract is returned with every query.
See [ADR 0003](../adr/0003-budget-constrained-ten-million-retrieval.md) and the
[ten-million runbook](../ten_million_scale_runbook.md).

## Asynchronous Serving

The request path now treats CPU inference and remote I/O as different resources.
One service instance owns one pinned CLIP/CSD encoder and a dedicated bounded
thread executor. The ASGI event loop remains available for uploads, health
checks, Qdrant, PostgreSQL, telemetry, and catalog calls.

An admitted request follows this sequence:

1. validate and decode the upload away from the event loop;
2. enter the bounded inference queue;
3. encode CLIP and CSD through the single model owner;
4. release the model slot before waiting for Qdrant and Neon;
5. construct the top-ten response; and
6. flush ordered completion telemetry outside the response's critical path.

Each Cloudflare shard permits one active inference and 24 waiting inferences.
Queue and inference waits have explicit deadlines, and saturation returns a
stable `503 encoder_busy` response instead of allocating an unbounded backlog.
Cancellation and shutdown release model, HTTP, database, telemetry, and executor
resources in a defined order.

See [ADR 0004](../adr/0004-async-online-serving.md) and the
[public API documentation](../public_image_search_api.md).

## Stream-Day Deployment

The Cloudflare Worker now hashes the trusted `CF-Connecting-IP` value to one of
three named Container shards. Runtime status, visit telemetry, and image search
from the same source therefore reach the same model process. The deployment has
a hard maximum of three 2-vCPU, 6-GiB Containers and each sleeps after 15 idle
minutes.

The configured burst envelope is:

| Control | Value |
| --- | ---: |
| Container shards | 3 |
| Concurrent model owners | 3 total |
| Waiting requests | 24 per shard |
| Active-or-waiting requests | 75 total |
| Queue deadline | 120 seconds |
| Model deadline | 120 seconds |
| Browser deadline | 200 seconds |
| Searches per source IP | 12/minute |
| Searches per edge location | 120/minute |
| Idle shutdown | 15 minutes |

This is a burst buffer, not 75-way inference. Based on observed CPU CSD time, a
roughly balanced 20-to-50-person one-query burst should drain in approximately
one to two minutes after warmup. Shared NATs, uneven hashing, provider latency,
or simultaneous cold starts can make that slower. No 50-user hosted load test
has been completed, so the project does not claim a stream-day latency SLA yet.

A best-effort page-load beacon starts the visitor's assigned shard before they
select an image. `/api/runtime-status` reports that shard's state without waking
it, and the page shows the state as a red/green indicator. The status endpoint is
not a global health claim for all three shards.

## Experimental Retrieval Controls

The workbench contains four sliders under the intentionally honest label
`these might do something idk`:

- CLIP half A and half B;
- CSD half A and half B.

For a 512-dimensional CLIP query, the controls scale coordinate ranges 0-255 and
256-511. For a 768-dimensional CSD query, they scale ranges 0-383 and 384-767.
The complete query vector is L2-normalized again before cosine retrieval, and
the stored corpus vectors are never modified.

These halves are arbitrary latent coordinate blocks. They are not known subject,
color, composition, or style axes. Equal `1.0x` values reproduce the baseline
query direction; unequal values are an exploratory interface whose effects must
be judged empirically. Values are returned in the API response and recorded in
query telemetry so later evaluation can compare them.

## Visitor And Quality Telemetry

The page records a visit with its existing opaque browser session key. At the
trusted edge boundary, the canonical source IP is transformed using HMAC-SHA256
and a deployment secret. Only the keyed digest and hash-version label reach
PostgreSQL; ArtSearch does not persist the raw IP.

The local operations dashboard now reports:

- all-time distinct visitor hashes;
- distinct visitor hashes in the last 24 hours;
- distinct visitor hashes in the configured reporting window;
- total and rolling searches;
- p50 and p95 search latency;
- success and error rates;
- feedback coverage, judged hit rate, Precision@10, and nDCG@10; and
- intake, routing, embedding, Qdrant, and discovery health.

The visitor count is approximate. Shared public addresses can undercount people,
changing addresses can overcount them, and clients that block or fail the beacon
are absent. It must not be presented as authenticated-user analytics.

## CI/CD And Runtime Agreement

Pull requests and pushes to `main` now run Python lint and tests, PostgreSQL 17
plus pgvector migration checks, Worker type generation and TypeScript checks,
Docker Compose validation, and secret/build-context assertions. Tagged alpha
deployments serialize releases, require the protected GitHub environment, apply
forward-compatible migrations first, deploy the Worker and Container, and then
smoke-test public edge routes.

Application Python is pinned to CPython 3.12.14. The package, Container label,
Worker package, and release tag are checked for one release version. Airflow uses
its official Python 3.12 image and upstream constraints rather than inheriting an
incompatible application environment.

## Stream-Day Checklist

Before sharing the link on a stream:

1. confirm `/health/edge` is healthy;
2. load the page and wait for the assigned shard indicator to turn green;
3. use a few distinct networks to exercise likely shard assignments;
4. submit one ordinary query and confirm ten R2-backed results;
5. keep the operations dashboard open for queue, latency, errors, visitor count,
   provider usage, and feedback;
6. avoid changing model or Qdrant lineage immediately before the event; and
7. reduce the Container ceiling after the event if the burst profile is no
   longer needed.

## Known Limits And Next Work

- A real 10-, 25-, and 50-client hosted load test is still required.
- CSD ViT-L remains the dominant warm-query compute cost.
- IP sharding cannot distribute many viewers behind one shared public address.
- The four half-vector controls are exploratory, not learned interpretable axes.
- Cloudflare rate-limit counters are abuse controls, not globally exact quotas.
- The ten-million FAISS path needs corpus-scale benchmark evidence before public
  promotion.
- Artist opt-out, source-deletion propagation, and result reporting still need a
  complete operator workflow before broad public distribution.
- Classification and discovery do not establish attribution, permission, safety,
  or consent and do not override artist opt-outs.
